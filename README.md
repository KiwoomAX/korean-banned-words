# korean-banned-words

한국어 문서와 답변에서 쓰지 않을 단어의 목록입니다. 이 저장소는 그 목록의 정본이며, 데이터 한 파일과 형식 검사 하나만 담습니다.

## 이 저장소가 있는 이유

같은 목록이 두 곳에서 따로 관리되고 있었습니다. 한쪽만 고치면 내용이 어긋납니다. 두 소비자가 서로를 참조하게 만들 수는 없습니다. 한쪽은 사내 환경 전용이고 다른 쪽은 사내 밖에서도 쓰이므로, 어느 방향으로 참조하든 한쪽이 상대의 존재를 알아야 하기 때문입니다. 양쪽이 서로를 모르는 채 같은 목록을 쓰려면 중립 저장소가 필요합니다.

## 담는 것과 담지 않는 것

담는 것은 `korean-banned-words.json` 과 `validate.py` 둘입니다.

생성 스크립트는 담지 않습니다. 출력 형태가 소비자마다 다르기 때문입니다. 한쪽은 훅이 파싱하는 마크다운 표가 필요하고, 다른 쪽은 분류별 화살표 형식이 필요합니다. 출력 형태를 여기서 정하면 소비자가 늘 때마다 이 저장소를 고쳐야 합니다.

어떤 단어를 넣을지 말지도 검사하지 않습니다. 그것은 사람이 정합니다. `validate.py` 가 확인하는 것은 소비자가 읽을 수 있는 형태인지 하나뿐입니다.

## 데이터 형태

```json
{
  "id": "jaeda",
  "category": "native-verb",
  "match": "forms",
  "banned": ["재다", "잰다", "재는", "재지", "재어지다"],
  "replace": ["측정", "확인", "관측", "계산"],
  "scope": ["answer", "artifact", "living-doc"],
  "enabled": true,
  "evidence": { "kind": "user", "date": "2026-08-30",
                "quote": "재다 → 측정하다 오히려 더 편한 말이야" }
}
```

각 칸이 있는 이유는 다음과 같습니다.

`match` 는 검색 방식이 아니라 나열의 완전성 책임을 밝히는 칸입니다. 소비자는 두 값을 모두 같은 방식으로, 그 글자가 들어 있기만 하면 걸리도록 검색합니다. 한국어는 조사가 붙어 `재다가`·`재다를` 이 되므로 단어 경계로 막으면 그것들을 놓치기 때문입니다.

값이 둘인 이유는 책임이 다르다는 것입니다. `forms` 인 항목은 `banned` 에 활용형을 모두 적을 책임이 있고, `fragment` 인 항목은 어간만 적으면 됩니다. 그래서 `forms` 항목은 나열이 실제 기록에 나타난 활용형을 모두 담았는지 검사할 수 있고, `fragment` 항목은 그 검사가 필요 없습니다.

둘을 나눈 이유는 한국어 활용형이 많아 나열로는 계속 샌다는 것입니다. `짚` 을 `짚다`·`짚는다`·`짚어` 로 나열했더니 실제로 나타난 158건 가운데 30건만 걸렸습니다. `맞대` 는 나열한 형태가 한 번도 나타나지 않아 41건을 모두 놓쳤습니다. 반대로 `재다` 를 `재` 한 글자로 자르면 `재무`·`재현`·`재고` 가 모두 걸립니다. 그래서 어간이 다른 단어에 나타나지 않는 항목만 `fragment` 로 적고 나머지는 `forms` 로 적습니다.

`fragment` 를 쓸 때 한글 음절이 한 글자라는 것을 잊으면 안 됩니다. `맞대` 는 `맞대고`·`맞대는` 을 품지만 `맞댄` 은 품지 않습니다. `맞댄` 의 둘째 글자가 `대` 가 아니라 `댄` 이기 때문입니다. 그래서 어간이 여러 형태로 나뉘는 항목은 `banned` 에 어간을 여럿 적습니다.

`replace` 와 `instruction` 은 다릅니다. `replace` 는 바꿔 쓸 단어이고, `instruction` 은 바꿔 쓸 단어가 따로 없이 "가리키는 대상의 이름을 쓰라"처럼 지시로만 표현되는 항목에 씁니다. 지시를 `replace` 에 넣으면 생성된 문장이 어색해집니다.

`replace` 는 한자어 명사형으로 씁니다. "측정한다" 가 아니라 "측정" 입니다. 방향만 가리키는 지시보다 바꿔 쓸 글자를 그대로 박아 둔 지시가 훨씬 잘 지켜진다는 측정이 있었습니다. 대체어를 한자어로 박아 두면 금지어를 피하는 순간 한자어가 나옵니다.

`enabled` 가 `false` 인 항목은 지우지 않고 `disabled_reason` 과 함께 남깁니다. 지우면 몇 달 뒤 같은 이유로 다시 넣자는 논의가 되풀이됩니다.

`evidence.kind` 는 넷입니다. `user` 는 사용자가 직접 지적한 것, `measured` 는 숫자로 확인한 것, `reasoned` 는 논리 설명만 있는 것, `none` 은 근거를 찾지 못한 것입니다. `user` 와 `measured` 에는 날짜와 원문이 따라붙어야 합니다.

`scope` 는 이 항목이 어디에 걸리는지입니다. `answer` 는 사용자에게 보내는 답, `artifact` 는 사용자가 요구한 산출물 문서, `living-doc` 은 저장소의 살아 있는 문서입니다.

## 소비자가 쓰는 방법

이 저장소는 사용자 PC로 내려가지 않습니다. 내려가는 것은 소비자가 이 데이터로 만들어 낸 결과물이고, 그 결과물은 기존 배포 경로가 그대로 나릅니다.

소비자 저장소가 각자 이렇게 합니다.

1. 자기 저장소에 생성 스크립트를 둔다.
2. GitHub Actions 가 하루 한 번, 그리고 손으로 실행할 때 이 저장소의 데이터를 당겨온다.
3. 생성 결과가 자기 저장소의 것과 다르면 자기 저장소에 PR 을 연다.

당겨오는 쪽으로 정한 이유가 있습니다. 이 저장소가 소비자 저장소에 밀어 넣으려면 개인 접근 토큰을 비밀 값으로 보관해야 합니다. 소비자 쪽 Actions 가 스스로 당겨오면 기본 권한만으로 자기 저장소에 PR 을 열 수 있습니다.

생성된 파일 머리에는 "이 파일은 생성물이므로 직접 고치지 말고 데이터 저장소를 고치라"를 적습니다.

## 목록을 고치는 방법

```
python validate.py
```

`korean-banned-words.json` 을 고치고 위 명령이 통과하는지 확인한 뒤 PR 을 엽니다. `updated` 날짜도 함께 고칩니다. 소비자 저장소는 다음 당겨오기에서 변경을 받습니다.

항목을 새로 넣을 때는 `evidence` 를 반드시 채웁니다. 근거를 찾지 못했으면 `none` 으로 적습니다. 근거가 없다는 사실 자체가 나중에 그 항목을 다시 검토할 실마리가 됩니다.
